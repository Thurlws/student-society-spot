## SocConnect architecture
- Current state, open bugs and the roadmap live in `context/` (start with `context/README.md`); update those notes when work changes the picture.
- App data comes from `src/lib/api/` (`useData()`: one TanStack Query over the database, polled until realtime); pages never touch the database directly — keeps one seam for data.
- Permissions and multi-step writes are Postgres functions/RLS (join_society, decide_membership, register_for_event, support-request functions); mutations return `Outcome` `{ ok, error }` from `src/lib/validation.ts`, which only holds Zod form checks — the browser is never trusted.
- "Today" and times are real Europe/Dublin via `src/lib/format.ts`; societies are addressed by slug in the UI and mapped to ids in the data layer — keeps URLs stable.
- Date formatting is manual in `src/lib/format.ts` (no toLocaleDateString) to avoid SSR hydration mismatches.
- The app shell wraps every route except `/welcome` in `__root.tsx`.
- Calls: rooms/meetings live in `call_rooms`; LiveKit tokens (1h) are minted only by server functions in `src/lib/livekit.functions.ts` after an RLS membership check, with identity from the profile; guests use hashed, expiring `call_invites` codes at `/join/$code`. Without LiveKit, calls show "not available" — never simulated people.
- Recaps are written and stored server-side (`call_recaps`), rate-limited via `ai_usage`; transcripts are cleared by a nightly pg_cron job after the retention period — keeps AI cost and personal data bounded.
- AI calls go through server functions in `src/lib/calls.functions.ts`, with gateway helpers in server-only `src/lib/ai.server.ts` — keeps the API key off the client.
- Identity comes from Lovable Cloud auth via `src/lib/auth.tsx` (session, profile, `my_access()` roles); app pages live under `src/routes/_authenticated/` so signed-out visitors go to `/welcome` — never trust the browser for roles.
- Sign-up domains come from `university_domains` and are enforced by a database trigger on auth.users (`enforce_email_domain`); each account belongs to the university of its email domain (`university_members`) and can't move to another's. Platform admins, university admins and committee seats come only from `role_invites`, claimed on sign-in by `handle_new_user` → `claim_invites` (no admin by email domain) — keep these rules in the database, not the UI.
- Universities are data, not code: every society has a `university_id`, people see only their own university's societies and what hangs off them, and university admins manage only their own university. Society-scoped admin checks use `private.can_manage_society` / `private.can_manage_university` (platform admin, or that university's admin), never `has_role(..., 'platform_admin')` alone — so no university can reach another's data. `university_isolation.test.sql` proves it.
- Sessions of accounts that haven't signed in for a year are ended nightly (`end_lapsed_sessions`); the next sign-in needs the university mailbox again — that is the yearly check that someone is still a student.
- Every table, and every database function signed-in users can call, has rows in `dev/supabase/tests/permission_matrix.test.sql` (nine kinds of user, including a student at another university and a university admin); CI fails on a new callable owner-rights function that isn't there. Supabase grants new tables and functions to everyone by default, so new tables enable RLS and new SECURITY DEFINER functions `revoke execute ... from public, anon`.
- Events are changed only through `update_event`/`cancel_event` (registered people are told; cancelled events stay listed and refuse registrations); announcements can change only title, body and pin, and show "edited" — so nobody is surprised by a silent change.
- Discussion moderation: authors delete their own messages, committees and admins (platform, or the society's university) remove any (`delete_message`), and members report to the committee queue and `/admin` (`report_message`). Reports about a committee member's own message go to the rest of the committee. Reports keep a short excerpt because admins can't read society channels.
- Browser journeys in `e2e/` (Playwright) run only against the local stack, with sign-in read from Mailpit; the config refuses any other backend.
- Platform admins (every university) and university admins (their own) manage societies and committees at `/admin`; platform admins also add universities, their domains and admins there. RLS policies are the security boundary. Permission helpers (`has_role`, `is_society_member`, `is_society_committee`, `society_visible`, `can_see_profile`, `user_university`, `can_manage_university`, `can_manage_society`) live in the `private` schema so the API can't call them — call them as `private.*` and never create SECURITY DEFINER helpers in `public`.
- Read policies never use `USING (true)`: profiles go through `can_see_profile` (self, admins, committee, shared society), society-scoped rows through `society_visible`, resources/proposals to members/committees — keeps personal data to the people who need it.
- `.env` (public backend URL/key only) is committed; real secrets live in Cloud secrets — published builds read `.env` from the repo and break without it.
- Society AI lives in authenticated `society-ai.functions.ts`, using RLS-scoped real records, database-locked quotas and durable availability state; recommendations use the ranking RPC and daily per-user context-aware cache to bound cost and prevent invented plans.
- The shared profile form offers the official TU Dublin undergraduate catalogue to TU Dublin members (catalogues are keyed by university slug in `profile-form.tsx`); students elsewhere type their course. Onboarding and profile editing use the same form.
- Official society data (`source = 'tudublin'` rows: logo, banner, campus, links, join/official URLs, extra sections) is imported from societies.tudublin.ie by generated migrations matched on `(source, source_id)`; refreshes never overwrite committee-edited tagline/description/meets, and `guard_society_update` keeps join/official URLs and source fields admin/import-only.
- Visual design lives in `src/styles.css` tokens: granite background, ink text, one TU Dublin blue `--primary` (#004c6c), and `--soc-*` society colours taken from Dublin's Georgian doors (keys match the database `accent` values). Bricolage Grotesque for headings, Plus Jakarta Sans for text. The logo tile (`bg-brand`) is the only gradient; cards don't lift on hover, labels are sentence case, and meta lines use commas, not dots.
- Society cards and pages show the official banner and logo from societies.tudublin.ie through `SocietyBanner`/`SocietyAvatar`, which fall back to the society's colour and icon when an image is missing or broken (a few official images are). The images are linked, not copied into the repo, because republishing rights haven't been confirmed.
- Society Pulse places each society next to the interests it lists (`src/lib/pulse-layout.ts`: deterministic, overlap-tested) instead of drawing a link for every pair that shares an interest, which turns into an unreadable hairball once there are dozens of societies. The side panel's search and lists are the keyboard path; the map is the overview.
